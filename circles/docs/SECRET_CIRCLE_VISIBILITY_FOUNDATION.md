# Secret circle visibility foundation

Circle `visibility` is separate from the existing policies:

- `visibility` (`public` or `secret`) controls whether a viewer may discover or read a circle. Missing values are `public` for backward compatibility.
- `isPublic` continues to control immediate versus approval-based admission.
- `moderationStatus` controls lifecycle availability.
- `accessRules` and member groups control module and action permissions.

Secret visibility requires a canonical `Members` record. Circle member counts, creator status, chat membership, groups, and ordinary superadmin status do not grant read access. User/profile circles always behave as public.

Initially, only an authenticated superadmin may create or transition a normal circle or project to secret visibility. Phase 2 protects direct circle routes, circle metadata, and circle-owned private media through the central read policy. Phase 3A1 protects direct Mongo discovery through maps, deterministic search, circle/project lists and pickers, bookmarks and pins, structural summaries, and anonymous public counts.

Phase 3A2 excludes secret ordinary circles and projects from the public Qdrant collection. Public-to-secret transitions delete and verify the public vector before committing visibility, then reconcile it again afterward; secret-to-public transitions commit public visibility before indexing. Full rebuilds purge stale secret Circle vectors before public upserts, and a manual server-side reconciliation helper is available without automatic startup deletion.

Phase 3B0 applies the same public-only storage rule to posts, tasks/shifts, events, goals, issues, and proposals. Canonical resource and owner records are checked before and after publication. Circle transitions purge affected derived vectors both before and after becoming secret, ownership changes and deletions reconcile synchronously, and full/manual reconciliation removes secret-owned and deleted-resource orphan points across all six public collections. No private vector collection is introduced.

Phase 3B1a establishes `Post.feedId -> Feed.circleId -> Circle` as the base user-facing Post access boundary. Browser-facing Feed actions derive viewer identity from the signed session, global Feed IDs are filtered by visibility and lifecycle before Post pagination, and direct Post/Discussion/comment reads fail with neutral absence unless the owning Circle is readable. Public user-Feed lookup keeps its requested profile separate from the authenticated viewer. New Discussions store a canonical Feed ID; legacy Discussion records without resolvable Feed ownership fail closed.

Phase 3B1b1 adds a second read boundary for source-bound Posts. Task, Goal, Issue, Proposal, and system Funding noticeboard Posts require their canonical source Circle to be readable; Event discussion and noticeboard Posts require every canonical host Circle to be readable. Funding uses a dedicated server-controlled source marker outside the generic shadow `parentItemType`, with legacy noticeboard Posts recognized only through the canonical Funding Ask backlink. Missing or malformed trusted sources fail closed. Source-bound Posts are excluded by Mongo before Feed pagination, and direct Post resolution returns the same neutral absence as a missing Post.

Phase 3B1b2a sanitizes internal previews on the server before readable Posts reach ordinary clients, including editor/composer preview lookup. Circle, Post, Task, Event, Goal, Issue, Proposal, and Funding previews use the same canonical resolver and require every canonical owner Circle to be readable; Post previews reuse central Post/source authorization and Event previews require every canonical host. The resolver returns only renderer-required fields plus a separately derived canonical URL. Missing, malformed, deleted, unsupported, suspended, removed, or inaccessible preview sources lose all preview identity and data, the corresponding identifying content token is replaced with neutral text, and the client has no raw-URL fallback. Shared-original handling is implemented by Phase 3B1b2b, Post/shared-original Circle-mention sanitation is implemented by Phase 3B1b2c1, comment sanitation remains for Phase 3B1b2c2, and Phase 3B1b3 write hardening remains incomplete.

Phase 3B1b2b safely hydrates shared originals through that same server-side nested-content boundary. Ordinary-client reads never receive raw `sharedPostId`; inaccessible, malformed, missing, or cyclic originals produce one neutral unavailable state, while readable originals produce a minimal renderer DTO with a server-derived canonical link. Shared originals reuse Phase 3B1b2a internal-preview sanitization before DTO derivation. Nested-share presentation is deliberately limited to depth 1, so an immediate readable original remains visible but its own share identity and data are omitted. Post/shared-original Circle-mention sanitation is implemented by Phase 3B1b2c1, comment sanitation remains for Phase 3B1b2c2, Phase 3B1b3 share/write restrictions remain deferred, and Secret Circles remain disabled.

Phase 3B1b2c1 implements canonical Circle-mention sanitation for Posts and readable shared originals. Content is authoritative: complete labeled single-segment `/circles/<identifier>` references are resolved under the central Circle read and lifecycle policy, readable references are rewritten to server-derived `[canonical name](/circles/canonical-handle)` Markdown, and every malformed, missing, deleted, lifecycle-unreadable, or inaccessible reference becomes exactly `Unavailable Circle`. Raw Post `mentions` and `mentionsDisplay` are stripped from ordinary-client Post reads, and Post-level unrestricted mention hydration has been removed. User mentions remain readable through the existing user Circle public invariant.

Phase 3B1b2c2a applies that same canonical policy to normal comments and replies after their parent Post is authorized. Roots and replies are sanitized together in one read batch, raw normal-comment mention hydration has been removed, and ordinary-client create/edit returns are sanitized after the existing persistence and notification flow. The common Feed and Discussion comment clients replace successful optimistic edits with the sanitized server result. Highlighted-comment aggregations, nested `getDiscussionWithComments` output, Discussion-specific and Event-alternate comment APIs remain deferred to Phase 3B1b2c2b. Mention write and notification hardening remain Phase 3B1b3 or later, and Secret Circles remain disabled.

Phase 3B1b2c2b1 applies canonical comment-mention sanitation to highlighted comments after Post/source/user-group access filtering and Post nested-content sanitation. Full Post, multi-feed, and single-feed reads share one batching and reattachment helper, and their unrestricted highlighted-mentioned-Circle hydration has been removed while highlighted author, reaction, selection, and ranking behavior is preserved. Phase 3B1b2c2b Discussion and Event alternate APIs remain deferred, Phase 3B1b3 write hardening remains deferred, and Secret Circles remain disabled.

Phase 3B1b2c2b2a protects the alternate Discussion APIs. Nested Discussion comments are projected through an explicit ordinary-client Comment DTO after canonical Post access, then the complete flat roots/replies array is sanitized in one batch before the existing outer Post sanitizer runs. The DTO filters legacy arbitrary top-level fields, normalizes reaction counts to finite non-negative integers, and serializes `editedAt` only when it is a valid persisted Date. The Discussion-specific add action now requires a canonically readable Discussion parent before feature authorization or insertion, forces server-controlled empty initial reactions and normal undeleted/unedited state, and returns one explicitly projected and sanitized item. Persisted arbitrary-field rejection and broader write validation remain deferred to Phase 3B1b3. Because the Event alternate APIs reuse the same low-level helpers, they inherit only this safer response-shape narrowing; Event authorization, shadow binding, post-type handling, and Comment sanitation remain deferred to Phase 3B1b2c2b2b. Pin/close pre-authorization hydration remains separate mutation-order work, although those actions do not return the hydrated comments. Secret Circles remain disabled.

Phase 3B1b2c2b2b1 protects the alternate Event comment GET. The action establishes canonical all-host Event-owner readability before returning an Event without a comment shadow, so a missing shadow no longer bypasses Secret Circle access. When a shadow is present, central Post/source authorization runs first and the shadow must match the requested post, Event parent, Feed, and primary Circle identities. Current `postType='event'` shadows are supported; legacy `postType='discussion'` shadows are accepted only under those same strict bindings, with every malformed or mismatched shape failing closed. Authorized nested comments are loaded neutrally by Post ID, projected through `toCommentDto`, and passed as one roots-and-replies batch through `sanitizeCommentMentions`. Event ADD remains deferred to Phase 3B1b2c2b2b2, broader Event/calendar/ICS privacy remains later work, and Secret Circles remain disabled.

Phase 3B1b2c2b2b2 protects the alternate Event comment ADD. The mutation now requires the same canonical readable shadow/Event binding as the read path, with no superadmin nonmember bypass, before checking that the primary and every deduplicated host Circle are write-available. Feature authorization uses the canonical resolved primary Circle, and insertion uses a neutral authorization-assuming Comment creation primitive with server-controlled identity, parent Post, timestamps, reaction state, reply count, and undeleted/unedited create state. The immediate result is projected through `toCommentDto` and passed through one `sanitizeCommentMentions` batch. Event stage/product rules are unchanged; broader Phase 3B1b3 validation and parent/mention/notification hardening, and broader Event/calendar/ICS privacy remain deferred. Secret Circles remain disabled.

Phase 3B1b3a adds the authoritative Circle-mention write resolver without integrating it into production write actions. Authored content is authoritative: supported structured Circle links resolve server-side by canonical ObjectId or current handle, require central readability, and are rewritten with the current escaped Circle name and canonical handle. Secret references require current canonical `Members` membership with no superadmin nonmember bypass, while user/profile Circles preserve their public invariant. `Mention[]` is derived and deduplicated by canonical Circle ID in first-occurrence order; malformed, missing, lifecycle-unreadable, or inaccessible structured references reject the entire result with one neutral unavailable message. Post action integration remains Phase 3B1b3b, Comment action integration remains Phase 3B1b3c, notifications remain later work, and Secret Circles remain disabled.

Phase 3B1b3b integrates that resolver into main Post create and content edit before persistence, vector publication, or mention notifications. Persisted Post content and deduplicated `Mention[]` are server-derived, forged client mention metadata is ignored, and Secret references require current membership on both create and edit. Ordinary Post creation now permits only base Post, Community, and Discussion types; source-owned types are rejected neutrally. The alternate Discussion create surface now builds an explicit title/content/location/media payload, forces `postType='discussion'`, derives canonical mentions, and cannot persist arbitrary source, internal-preview, share, counter, timestamp, or unknown metadata. It does not support `sharedPostId`. Existing mention notifications consume the canonical derived targets, while notification payload privacy remains later work. Comment write integration is completed in Phase 3B1b3c, internal-preview write canonicalization in Phase 3B1b3d, and shared-post hardening in Phase 3B1b3e below; Event host consistency remains Phase 3B1b3f, and source-bound edit/delete authorization remains Phase 3B1c. Secret Circles remain disabled.

Phase 3B1b3c applies canonical structured Circle-reference writes to normal Comment create/edit and alternate Discussion/Event Comment create. Comment content and deduplicated `Mention[]` are server-derived, caller mention metadata and other broad alternate-create fields are discarded, and edits are denied without mutation when a retained Secret reference is no longer readable by the author. Supplied `parentCommentId` values must be valid, existing Comments on the same canonical Post; malformed, missing, and cross-Post parents fail with one neutral Comment-target error before insertion, reply-counter changes, or notifications. Reply counters update only after validated child insertion, and mention notification targets come from canonical mentions; notification payload privacy remains later work. Broader source-bound Comment edit/delete/reaction authorization remains Phase 3B1c. Secret Circles remain disabled.

Phase 3B1b3d canonicalizes internal-link preview writes for ordinary Post create and edit. The complete client type/ID/URL shape identifies a candidate only: the server re-resolves set/change requests through the canonical read resolver and persists only the canonical type, resource ID, and URL. Caller preview URLs are not authoritative, caller `internalPreviewData` is never persisted, valid uppercase resource ObjectId candidates normalize to canonical lowercase, and the read-time payload remains derived. Unreadable, malformed, or partial preview requests fail neutrally before persistence, vector publication, upload, or notification; Secret targets require current canonical membership and ordinary superadmin status provides no nonmember bypass. Omitting all three preview fields preserves the stored canonical triple without re-resolution, while supplying all three as empty explicitly removes every persisted preview field; replacing an internal preview with an external preview sends that removal intent before retaining the normal external fields. Only the canonical Circle, Post, Task/Shift, Event, Goal, Issue, Proposal, and Funding route forms emitted by the read resolver satisfy the `internalPreviewUrl` model. Production orchestration tests exercise the real write resolver with the central visibility/lifecycle predicate, and explicit removal is covered at the `updatePost` Mongo `$unset` operation seam. External preview behavior is otherwise unchanged. Phase 3B1b3e shared-original write work is completed below; Phase 3B1b3f Event host consistency remains deferred, and Secret Circles remain disabled.

Phase 3B1b3e completes shared-original write authorization for ordinary Post creation. A caller-supplied `sharedPostId` is only a candidate: the server resolves it through the canonical readable shared-original path, persists the canonical lowercase Post ObjectId, and fails unreadable Secret or source-bound originals neutrally with `Original post unavailable.` before preview resolution, persistence, vector publication, upload, or notification. Current canonical membership and lifecycle/source ownership rules apply, and superadmin status provides no nonmember content-read bypass. Caller `sharedPostData` and nested original metadata are never authoritative or persisted. Sharing remains creation-only: ordinary edits preserve stored shared state without re-resolution and ignore attempted shared-field changes, including after later readability loss. Alternate Discussion creation does not support shared originals and strips shared fields without a lookup; server-generated Task/Event/Goal/Issue/Proposal/Funding Posts continue to use explicit server-owned construction. Phase 3B1b3f Event host consistency and broader Phase 3B1c Post mutations remain deferred, and Secret Circles remain disabled.

Phase 3B1b3f hardens new and changed Event host sets through one production write policy used by create, update, stage publication, and fallback-shadow creation. The effective host set is the primary `circleId` plus optional `hostCircleIds`, validated as canonical ObjectIds and deduplicated in primary-first order; missing, null, or empty top-level `hostCircleIds` retains primary-only compatibility, while malformed ordinary writes—including explicit arrays containing empty or whitespace-only elements—fail neutrally. Every host must have one effective visibility: missing visibility is public, user/profile Circles remain public, and mixed public/Secret sets are rejected. Every Secret host requires the authenticated actor's current canonical `Members` membership, with no admin, moderator, creator, or superadmin nonmember bypass, and active-only lifecycle/write availability remains enforced for every host before media, Event, shadow, vector, noticeboard, or notification effects. Event comment shadows remain single-primary-host resources: fallback creation derives that canonical primary Circle from the Event server-side, exposes no caller-selected Circle argument, and reuses an existing shadow only after strict Event/Post/Feed/Circle/source binding. Multi-host noticeboard publication remains one server-derived Post per validated host. Existing mixed-host Events are not migrated and fail closed on subsequent edits or publication transitions; existing all-host Event reads and internal previews are unchanged. Broader Phase 3B1c mutations remain deferred, and Secret Circles remain disabled.

Phase 3B1c1 protects ordinary Post content edits with canonical mutation-time resolution. `updatePostAction` now reuses the central readable Post context, including Post-to-Feed-to-Circle ownership, Circle visibility and current Secret membership, readable lifecycle, view-feature, author-status, user-group, and canonical source policies; there is no ordinary superadmin nonmember bypass. The canonical Feed Circle must additionally be writable, so normal Circles must be active. Recognized Task, Event, Goal, Issue, Proposal, and explicit or resolver-classified legacy Funding source Posts cannot be edited through the ordinary action even by their shadow author or a privileged role; trusted server-owned source synchronization continues to call low-level `updatePost` directly. Malformed, missing, inaccessible, lifecycle-unwritable, source-owned, and caller-Circle-mismatched edit targets fail neutrally with `Post unavailable` before content/preview/mention processing, media upload, database/vector mutation, or notification. The existing source policy validates the legacy Funding `noticeboardPostId` backlink when it treats that marker as source-owned, but does not enforce Task/Event/Goal/Issue/Proposal or explicit Funding back-references; broader reference-integrity work is deferred.

Phase 3B1c2 protects ordinary Post deletion with the same canonical current read and writable-lifecycle policy before existing author, moderator, module, and feature checks. Recognized Task, Event, Goal, Issue, Proposal, explicit Funding, and complete legacy Funding source Posts are unavailable to ordinary deletion; Event comment and noticeboard Posts are covered by their canonical markers. A delete-only reverse lookup also protects Shift noticeboard Posts owned by `Task.noticeboardPostId`, without treating copied Task previews as source-owned. Ordinary preview Posts and Discussion Posts retain normal deletion behavior. Secret membership, user-group access, source readability, author visibility/status, and active lifecycle are mandatory, with no superadmin, Circle-admin, or moderator nonmember bypass. Every authenticated denial is neutral (`Post unavailable`) and occurs before low-level deletion or route revalidation. Trusted low-level `deletePost` rollback and Event cleanup callers remain authorization-free and unchanged, including existing vector behavior. Source-reference repair, MinIO/media cleanup, notification cleanup, transactions, Phase 3B1c3+, and Secret enablement remain deferred; Secret Circles remain disabled.

Phase 3B1c3a protects ordinary Post likes and unlikes with one production reaction policy and orchestration seam. Every mutation reauthorizes current canonical Post-to-Feed-to-Circle readability through `resolveReadablePostContext`, including current Secret membership, author status, user groups, module/view access, source readability, and all-host Event readability; the canonical owning Feed Circle must additionally be writable, and the existing Post reaction feature remains additive. Like and unlike use the same current-access rule, with no superadmin, Circle-admin, or moderator nonmember bypass. Readable Task, Event, Goal, Issue, Proposal, explicit Funding, and compatible legacy Funding Posts remain reactable; Shift noticeboard Posts remain ordinary readable noticeboard Posts and do not use the delete-only Task reverse lookup. Duplicate sequential likes and absent/repeated unlikes are no-ops, so duplicate notifications and negative counters are avoided. Concurrent duplicate-like uniqueness remains deferred without an index migration, Comment canonical reaction authorization remains Phase 3B1c3b, and Secret Circles remain disabled.

Phase 3B1c3b protects Comment likes and unlikes with one production Comment reaction policy and orchestration seam. Every mutation reauthorizes the canonical current Comment-to-Post binding and reuses the Phase 3B1c3a Post reaction policy, including current Post/source readability, current Secret membership, Post user groups and author availability, module/view and reaction-feature authorization, all-host Event readability, and writable lifecycle for only the canonical owning Feed Circle. Like and unlike use the same current-access rule, with no superadmin, Circle-admin, or moderator nonmember bypass; soft-deleted Comments are unavailable. Canonical alternate Event Comment shadows additionally reuse strict `isEventShadowBound` validation, while Event noticeboard Comments remain generic feed Comments. Readable Task, Goal, Issue, and Proposal source-shadow Comments remain reactable without new reverse-backlink requirements. Duplicate likes and absent/repeated unlikes preserve their no-op counter, highlight, and notification behavior. Strict non-Event shadow backlinks and Comment create/edit/delete hardening remain deferred, and Secret Circles remain disabled.

Phase 3B1c4 protects browser-facing Comment creation through one canonical orchestration boundary. The target Post is reauthorized through the central Post-to-Feed-to-Circle and source-read policies, including current Secret membership, readable Post author, Post user groups, and writable owning Circle, before semantic Comment permission is checked: ordinary and Funding/noticeboard Posts use `feed.comment`, Community uses its existing participation feature, Discussion uses `discussions.comment`, Task/Goal/Issue detail shadows use their module Comment features, and Proposal detail shadows retain `feed.comment` because no `proposals.comment` feature exists. Task, Goal, Issue, and Proposal detail shadows require their persisted source `commentPostId` backlink, while ordinary source noticeboards remain generic. Event alternate targets route through the existing strict Event creator, which reloads and revalidates the current Event, canonical shadow binding, primary Circle, and host set at mutation time and requires every host writable; Event noticeboards remain generic and do not inherit that all-host-write rule. Discussions route through the existing closed-aware creator. A reply parent must belong to the same authorized Post, and target authorization plus parent validation precede mention resolution. Authenticated denials return neutral `Content unavailable`, with no superadmin, Circle-admin, or moderator nonmember Secret bypass. Existing soft-deleted-parent behavior and dedicated Event/Discussion side-effect differences remain unchanged and deferred, Comment edit/delete remain deferred, and Secret Circles remain disabled.

Phase 3B1c5a protects browser-facing Comment edits through a production canonical mutation resolver and edit orchestration seam. Every edit requires the current canonical Comment-to-Post binding and central readable Post context, including current Secret membership, Post user groups, Post-author availability, module/view policy, and source/Event readability, plus a writable owning Circle. Stored Comment DID equality remains the sole edit authority: superadmin, Circle admin, moderator, Post author, and source roles receive no non-author or nonmember bypass, and an author who has lost current target access cannot edit by retaining the Comment ID. The shared creation/edit semantic classifier strictly validates Task, Goal, Issue, and Proposal detail-shadow backlinks and selects `tasks.comment`, `goals.comment`, `issues.comment`, and the existing Proposal `feed.comment` fallback; ordinary Event, Funding, Task/Shift, and preview-bearing noticeboards remain generic. Alternate Event edits reload the current Event at the mutation boundary, require the strict shadow/primary binding and every current host to be readable and writable, while Event noticeboard edits require only canonical source readability and a writable owning Circle. Existing Discussion Comments remain author-editable when open, pinned, or closed. Tombstoned Comments cannot be edited, and all authenticated denials return `Content unavailable` before mention resolution, update, or notification. Successful edits preserve mention replacement and newly-added-only notifications without Post activity, highlight, or revalidation changes. Comment delete/tombstone/counter/reaction/highlight/source cleanup remains Phase 3B1c5b; activity/highlight normalization and privacy-erasure/notification-retention redesign remain deferred. Secret Circles remain disabled.
