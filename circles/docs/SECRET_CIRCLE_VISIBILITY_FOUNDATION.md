# Secret circle visibility foundation

Circle `visibility` is separate from the existing policies:

- `visibility` (`public` or `secret`) controls whether a viewer may discover or read a circle. Missing values are `public` for backward compatibility.
- `isPublic` continues to control immediate versus approval-based admission.
- `moderationStatus` controls lifecycle availability.
- `accessRules` and member groups control module and action permissions.

Secret visibility requires a canonical `Members` record. Circle member counts, creator status, chat membership, groups, and ordinary superadmin status do not grant read access. User/profile circles always behave as public.

Initially, only an authenticated superadmin may create or transition a normal circle or project to secret visibility. Phase 2 protects direct circle routes, circle metadata, and circle-owned private media through the central read policy. Phase 3A1 protects direct Mongo discovery through maps, deterministic search, circle/project lists and pickers, bookmarks and pins, structural summaries, and anonymous public counts.

Phase 3A2 excludes secret ordinary circles and projects from the public Qdrant collection. Public-to-secret transitions delete and verify the public vector before committing visibility, then reconcile it again afterward; secret-to-public transitions commit public visibility before indexing. Full rebuilds purge stale secret Circle vectors before public upserts, and a manual server-side reconciliation helper is available without automatic startup deletion.

Phase 3B0 applies the same public-only storage rule to posts, tasks/shifts, events, goals, issues, and proposals. Canonical resource and owner records are checked before and after publication. Circle transitions purge affected derived vectors both before and after becoming secret, ownership changes and deletions reconcile synchronously, and full/manual reconciliation removes secret-owned and deleted-resource orphan points across all six public collections. No private vector collection is introduced.

Phase 3B1a establishes `Post.feedId -> Feed.circleId -> Circle` as the base user-facing Post access boundary. Browser-facing Feed actions derive viewer identity from the signed session, global Feed IDs are filtered by visibility and lifecycle before Post pagination, and direct Post/Discussion/comment reads fail with neutral absence unless the owning Circle is readable. Public user-Feed lookup keeps its requested profile separate from the authenticated viewer. New Discussions store a canonical Feed ID; legacy Discussion records without resolvable Feed ownership fail closed.

Phase 3B1b1 adds a second read boundary for source-bound Posts. Task, Goal, Issue, Proposal, and system Funding noticeboard Posts require their canonical source Circle to be readable; Event discussion and noticeboard Posts require every canonical host Circle to be readable. Funding uses a dedicated server-controlled source marker outside the generic shadow `parentItemType`, with legacy noticeboard Posts recognized only through the canonical Funding Ask backlink. Missing or malformed trusted sources fail closed. Source-bound Posts are excluded by Mongo before Feed pagination, and direct Post resolution returns the same neutral absence as a missing Post.

Phase 3B1b2a sanitizes internal previews on the server before readable Posts reach ordinary clients, including editor/composer preview lookup. Circle, Post, Task, Event, Goal, Issue, Proposal, and Funding previews use the same canonical resolver and require every canonical owner Circle to be readable; Post previews reuse central Post/source authorization and Event previews require every canonical host. The resolver returns only renderer-required fields plus a separately derived canonical URL. Missing, malformed, deleted, unsupported, suspended, removed, or inaccessible preview sources lose all preview identity and data, the corresponding identifying content token is replaced with neutral text, and the client has no raw-URL fallback. Shared-original handling is implemented by Phase 3B1b2b, Post/shared-original Circle-mention sanitation is implemented by Phase 3B1b2c1, comment sanitation remains for Phase 3B1b2c2, and Phase 3B1b3 write hardening remains incomplete.

Phase 3B1b2b safely hydrates shared originals through that same server-side nested-content boundary. Ordinary-client reads never receive raw `sharedPostId`; inaccessible, malformed, missing, or cyclic originals produce one neutral unavailable state, while readable originals produce a minimal renderer DTO with a server-derived canonical link. Shared originals reuse Phase 3B1b2a internal-preview sanitization before DTO derivation. Nested-share presentation is deliberately limited to depth 1, so an immediate readable original remains visible but its own share identity and data are omitted. Post/shared-original Circle-mention sanitation is implemented by Phase 3B1b2c1, comment sanitation remains for Phase 3B1b2c2, Phase 3B1b3 share/write restrictions remain deferred, and Secret Circles remain disabled.

Phase 3B1b2c1 implements canonical Circle-mention sanitation for Posts and readable shared originals. Content is authoritative: complete labeled single-segment `/circles/<identifier>` references are resolved under the central Circle read and lifecycle policy, readable references are rewritten to server-derived `[canonical name](/circles/canonical-handle)` Markdown, and every malformed, missing, deleted, lifecycle-unreadable, or inaccessible reference becomes exactly `Unavailable Circle`. Raw Post `mentions` and `mentionsDisplay` are stripped from ordinary-client Post reads, and Post-level unrestricted mention hydration has been removed. User mentions remain readable through the existing user Circle public invariant.

Phase 3B1b2c2a applies that same canonical policy to normal comments and replies after their parent Post is authorized. Roots and replies are sanitized together in one read batch, raw normal-comment mention hydration has been removed, and ordinary-client create/edit returns are sanitized after the existing persistence and notification flow. The common Feed and Discussion comment clients replace successful optimistic edits with the sanitized server result. Highlighted-comment aggregations, nested `getDiscussionWithComments` output, Discussion-specific and Event-alternate comment APIs remain deferred to Phase 3B1b2c2b. Mention write and notification hardening remain Phase 3B1b3 or later, and Secret Circles remain disabled.

Phase 3B1b2c2b1 applies canonical comment-mention sanitation to highlighted comments after Post/source/user-group access filtering and Post nested-content sanitation. Full Post, multi-feed, and single-feed reads share one batching and reattachment helper, and their unrestricted highlighted-mentioned-Circle hydration has been removed while highlighted author, reaction, selection, and ranking behavior is preserved. Phase 3B1b2c2b Discussion and Event alternate APIs remain deferred, Phase 3B1b3 write hardening remains deferred, and Secret Circles remain disabled.

Phase 3B1b2c2b2a protects the alternate Discussion APIs. Nested Discussion comments are projected through an explicit ordinary-client Comment DTO after canonical Post access, then the complete flat roots/replies array is sanitized in one batch before the existing outer Post sanitizer runs. The DTO filters legacy arbitrary top-level fields, normalizes reaction counts to finite non-negative integers, and serializes `editedAt` only when it is a valid persisted Date. The Discussion-specific add action now requires a canonically readable Discussion parent before feature authorization or insertion, forces server-controlled empty initial reactions and normal undeleted/unedited state, and returns one explicitly projected and sanitized item. Persisted arbitrary-field rejection and broader write validation remain deferred to Phase 3B1b3. Because the Event alternate APIs reuse the same low-level helpers, they inherit only this safer response-shape narrowing; Event authorization, shadow binding, post-type handling, and Comment sanitation remain deferred to Phase 3B1b2c2b2b. Pin/close pre-authorization hydration remains separate mutation-order work, although those actions do not return the hydrated comments. Secret Circles remain disabled.

Phase 3B1b2c2b2b1 protects the alternate Event comment GET. The action establishes canonical all-host Event-owner readability before returning an Event without a comment shadow, so a missing shadow no longer bypasses Secret Circle access. When a shadow is present, central Post/source authorization runs first and the shadow must match the requested post, Event parent, Feed, and primary Circle identities. Current `postType='event'` shadows are supported; legacy `postType='discussion'` shadows are accepted only under those same strict bindings, with every malformed or mismatched shape failing closed. Authorized nested comments are loaded neutrally by Post ID, projected through `toCommentDto`, and passed as one roots-and-replies batch through `sanitizeCommentMentions`. Event ADD remains deferred to Phase 3B1b2c2b2b2, broader Event/calendar/ICS privacy remains later work, and Secret Circles remain disabled.

Phase 3B1b2c2b2b2 protects the alternate Event comment ADD. The mutation now requires the same canonical readable shadow/Event binding as the read path, with no superadmin nonmember bypass, before checking that the primary and every deduplicated host Circle are write-available. Feature authorization uses the canonical resolved primary Circle, and insertion uses a neutral authorization-assuming Comment creation primitive with server-controlled identity, parent Post, timestamps, reaction state, reply count, and undeleted/unedited create state. The immediate result is projected through `toCommentDto` and passed through one `sanitizeCommentMentions` batch. Event stage/product rules are unchanged; broader Phase 3B1b3 validation and parent/mention/notification hardening, and broader Event/calendar/ICS privacy remain deferred. Secret Circles remain disabled.

Phase 3B1b3a adds the authoritative Circle-mention write resolver without integrating it into production write actions. Authored content is authoritative: supported structured Circle links resolve server-side by canonical ObjectId or current handle, require central readability, and are rewritten with the current escaped Circle name and canonical handle. Secret references require current canonical `Members` membership with no superadmin nonmember bypass, while user/profile Circles preserve their public invariant. `Mention[]` is derived and deduplicated by canonical Circle ID in first-occurrence order; malformed, missing, lifecycle-unreadable, or inaccessible structured references reject the entire result with one neutral unavailable message. Post action integration remains Phase 3B1b3b, Comment action integration remains Phase 3B1b3c, notifications remain later work, and Secret Circles remain disabled.

Phase 3B1b3b integrates that resolver into main Post create and content edit before persistence, vector publication, or mention notifications. Persisted Post content and deduplicated `Mention[]` are server-derived, forged client mention metadata is ignored, and Secret references require current membership on both create and edit. Ordinary Post creation now permits only base Post, Community, and Discussion types; source-owned types are rejected neutrally. The alternate Discussion create surface now builds an explicit title/content/location/media payload, forces `postType='discussion'`, derives canonical mentions, and cannot persist arbitrary source, internal-preview, share, counter, timestamp, or unknown metadata. It does not support `sharedPostId`. Existing mention notifications consume the canonical derived targets, while notification payload privacy remains later work. Comment write integration remains Phase 3B1b3c, internal-preview write canonicalization remains Phase 3B1b3d, broader shared-post hardening remains Phase 3B1b3e, Event host consistency remains Phase 3B1b3f, and source-bound edit/delete authorization remains Phase 3B1c. Secret Circles remain disabled.

Phase 3B1b3c applies canonical structured Circle-reference writes to normal Comment create/edit and alternate Discussion/Event Comment create. Comment content and deduplicated `Mention[]` are server-derived, caller mention metadata and other broad alternate-create fields are discarded, and edits are denied without mutation when a retained Secret reference is no longer readable by the author. Supplied `parentCommentId` values must be valid, existing Comments on the same canonical Post; malformed, missing, and cross-Post parents fail with one neutral Comment-target error before insertion, reply-counter changes, or notifications. Reply counters update only after validated child insertion, and mention notification targets come from canonical mentions; notification payload privacy remains later work. Broader source-bound Comment edit/delete/reaction authorization remains Phase 3B1c. Secret Circles remain disabled.

Phase 3B1c Post interaction/notification hardening also remains incomplete. Other derived-resource authorization, public attachment URL/private upload selection, chat, notification, and admission surfaces remain release blockers, so Secret Circles must not be enabled in production yet.
